Micronaut Scala

Micronaut Scala compiler plugin and integration tests

Version: 1.0.0-SNAPSHOT

1 Introduction

Micronaut Scala lets you use Micronaut Framework from Scala 3. Its compiler plugin generates bean definitions, introspections and AOP proxies from your Scala classes during compilation.

The plugin adapts Scala declarations to Micronaut’s compile-time APIs. Micronaut Core provides the shared processing and runtime infrastructure; this project provides the Scala compiler integration and runtime support for Scala types.

Supported versions

The build supports Scala 3.10.0 and 3.3.9. Each compiler version has its own plugin artifact:

  • io.micronaut.scala:micronaut-inject-scala_3.10.0

  • io.micronaut.scala:micronaut-inject-scala_3.3.9

Choose the artifact that exactly matches your Scala compiler version. Compiler plugin APIs can change between releases, so using a different version can fail during compilation.

The test harness is published as io.micronaut.scala:micronaut-inject-scala-test_3.10.0. Runtime support is published as io.micronaut.scala:micronaut-runtime-scala and does not have a compiler-version suffix.

Micronaut Scala has its own version, independent of Micronaut Core. The current development version is 1.0.0-SNAPSHOT. The build requires JDK 25.

What is included

The integration supports dependency injection, bean introspection, AOP, configuration properties and annotation metadata. Runtime support includes converters for Scala collections and Option, along with Micronaut Serialization support for collections, Option and Scala 3 enums.

Scala 2 is not supported.

Start with Quick Start to configure the plugin. If you are new to Micronaut, Micronaut for Scala Developers introduces the main framework features with Scala examples.

2 Quick Start

To use Micronaut from Scala, add the compiler plugin to your build and the Scala runtime support to your application’s runtime dependencies. Use JDK 25 and choose a plugin artifact that matches your full Scala compiler version.

Add the dependencies

For a Gradle application using Scala 3.10.0, add these entries to your dependencies block:

scalaCompilerPlugins("io.micronaut.scala:micronaut-inject-scala_3.10.0:1.0.0-SNAPSHOT")
runtimeOnly("io.micronaut.scala:micronaut-runtime-scala:1.0.0-SNAPSHOT")

micronaut-inject-scala_3.10.0 runs during compilation and generates the classes Micronaut needs to create and inject your beans. micronaut-runtime-scala provides converters and serialization support for Scala types at runtime.

Keep the compiler plugin off the application runtime classpath. Its jar bundles Micronaut and ASM classes that can conflict with the application’s own dependencies.

See Build Tools for a fuller Gradle configuration and examples for Maven, sbt and Mill. Adding the plugin as an ordinary dependency does not register it with the Scala compiler.

Define and use a bean

Define a dependency as a bean with @Singleton:

@Singleton
class Translator:
  def hello: String = "Hello"

Then declare it as a constructor parameter in another bean:

@Singleton
class GreetingService(translator: Translator):
  def greet(name: String): String = s"${translator.hello}, $name"

Micronaut supplies Translator when it creates GreetingService. In an application context, calling getBean(classOf[GreetingService]).greet("Scala") returns Hello, Scala.

See Micronaut for Scala Developers for more about bean creation, qualifiers and the other framework features.

Match the compiler version

The suffix _3.10.0 is the full Scala compiler version. Do not shorten it to _3 or use it with a different compiler release. See Supported versions for the available variants.

The examples use the development version 1.0.0-SNAPSHOT. When using a released version, replace that version in both dependencies.

3 Micronaut for Scala Developers

Micronaut provides dependency injection, configuration binding, introspection and AOP. This chapter introduces those features through Scala examples.

The Scala compiler plugin runs Micronaut’s compile-time processing while your Scala sources are compiled. You use the same Micronaut annotations and runtime APIs as you would in a Java application.

Compile-time processing and runtime bean creation

During compilation, the plugin generates a BeanDefinition for each bean. It records how to construct the bean, which dependencies it needs and which qualifiers apply. At runtime, Micronaut uses these definitions to create beans and resolve their dependencies, avoiding reflective discovery of that metadata.

This does not mean every dependency problem is a compile error. A missing bean or an ambiguous qualifier can still cause an error when Micronaut tries to create the bean at runtime.

Scala also has different rules for Java annotation arguments. See Annotations when adapting an example from the Java guide.

Dependency injection

A bean is an object managed by Micronaut. Start by defining a trait for a dependency:

trait Engine:
  def start(): String

Annotate each implementation with @Singleton to make it a bean. Here, @Named distinguishes two implementations of the same trait:

@Singleton
@Named("v6")
class V6Engine extends Engine:
  def start(): String = "V6 starting"

@Singleton
@Named("v8")
class V8Engine extends Engine:
  def start(): String = "V8 starting"

Declare the dependency as a constructor parameter. A qualifier, such as @Named, selects an implementation when several beans have the required type:

@Singleton
class Vehicle(@Named("v8") engine: Engine):
  def start(): String = engine.start()

ApplicationContext.run().getBean(classOf[Vehicle]) creates a Vehicle with V8Engine supplied. If no matching engine bean is available, creating the Vehicle fails at runtime.

Prefer constructor injection in Scala. Dependencies are available as soon as the class is constructed, and a unit test can supply them directly with new. Micronaut also supports field and setter injection with @Inject.

Scopes

A scope controls a bean’s lifetime. @Singleton shares one instance within an application context. @Prototype creates a new instance for each injection or lookup:

@Prototype
class Journey:
  val id: String = java.util.UUID.randomUUID().toString

Other Micronaut scopes include @Context, @Refreshable and request scope in server applications.

Configuration properties

@ConfigurationProperties binds a class to a section of application configuration. The resulting object is a bean that other beans can inject:

@ConfigurationProperties("engine")
class EngineConfiguration(
    val manufacturer: String,
    // An absent property binds to `None` rather than failing the bean.
    val nickname: Option[String],
    val cylinders: List[Int]
)

Set engine.manufacturer to Ford and engine.cylinders to a list to supply the corresponding constructor values. nickname is optional: when its configuration property is absent, it binds to None. The List[Int] parameter receives a Scala list with each element converted to an integer.

These conversions require micronaut-runtime-scala on the runtime classpath. Scala Seq, Set and Map are also supported. A required parameter without a value or a default prevents the configuration bean from being created.

Bean introspection

@Introspected asks Micronaut to generate metadata for constructing a type and accessing its properties. Validation, data binding and serialization can use this metadata without discovering properties through reflection:

@Introspected
case class Book(title: String, pages: Int)

BeanIntrospection.getIntrospection(classOf[Book]) exposes title and pages as properties and can instantiate Book from their values. The case class’s constructor parameters supply its properties, and its generated accessors supply the getters.

Ordinary classes can also be introspected. The plugin recognises Scala val and var accessors as well as getter and setter pairs. A val is read-only; a var can also be written through its setter.

Serialization

Micronaut Serialization uses generated introspections to read and write objects. Mark a case class with @Serdeable to enable both directions:

@Serdeable
case class Order(id: String, quantity: Int)

An injected ObjectMapper writes this example as {"id":"A-1","quantity":3} and reads it back through the case class constructor. Add io.micronaut.serde:micronaut-serde-jackson to use the Jackson-based implementation.

For properties declared as Scala collections, Option or Scala 3 enums, also include micronaut-runtime-scala. See Serialization for JSON examples and the handling of missing optional fields.

Around advice

Aspect-oriented programming (AOP) lets an interceptor add behaviour around a method call. Common uses include logging, retries and transactions. Micronaut generates the proxy classes during compilation.

To define custom around advice, first declare an annotation marked with @Around:

@Around
@Retention(RetentionPolicy.RUNTIME)
@Target(Array(ElementType.TYPE, ElementType.METHOD))
class Audited extends StaticAnnotation, java.lang.annotation.Annotation:
  override def annotationType(): Class[? <: java.lang.annotation.Annotation] =
    classOf[Audited]

Then bind an interceptor to the annotation. The interceptor receives the call and invokes proceed() to continue to the original method:

@Singleton
@InterceptorBean(Array(classOf[Audited]))
class AuditInterceptor extends MethodInterceptor[Object, Object]:
  private val calls = ListBuffer.empty[String]

  def audited: Seq[String] = calls.toSeq

  override def intercept(context: MethodInvocationContext[Object, Object]): Object =
    calls += context.getMethodName
    context.proceed()

Apply the annotation to the methods you want to intercept, or to a class to advise its eligible methods:

@Singleton
class OrderService:
  @Audited
  def place(item: String): String = s"ordered $item"

  def quote(item: String): String = s"quote for $item"

Calling place runs the interceptor and returns ordered a book. Calling quote does not run the interceptor.

The annotation extends java.lang.annotation.Annotation because @InterceptorBean accepts a classOf[…​] argument with that bound. See Annotations for details.

The generated proxy extends the advised class and overrides its advised methods. A final class or advised method therefore causes a compilation error.

Introduction advice

Introduction advice supplies the implementation of abstract methods. This is how Micronaut implements declarative clients and repositories.

The interceptor uses the invocation context to decide how to answer each call:

@Singleton
class GreeterIntroduction extends MethodInterceptor[AnyRef, Object]:
  override def intercept(context: MethodInvocationContext[AnyRef, Object]): Object =
    s"${context.getMethodName}(${context.getParameterValues.mkString(", ")})"

An annotation marked with @Introduction enables the advice. @Type identifies the interceptor:

@Introduction
@Type(Array(classOf[GreeterIntroduction]))
@Retention(RetentionPolicy.RUNTIME)
@Target(Array(ElementType.TYPE))
class Stub extends StaticAnnotation

Apply the annotation to a trait or abstract class:

@Stub
trait Greeter:
  def greet(name: String): String

getBean(classOf[Greeter]).greet("Scala") returns greet(Scala), the value supplied by the interceptor. An abstract class can also have constructor dependencies and concrete methods; those methods keep their implementation.

Data access

Micronaut Data uses introduction advice to implement repositories. An entity can be a case class whose constructor parameters describe the mapped properties:

/** A book on the shelf.
  *
  * @param id the generated primary key, zero until the database assigns one
  * @param title the book's title
  * @param pages how many pages it has
  */
@MappedEntity
case class Book(
    @Id @GeneratedValue id: Long,
    title: String,
    pages: Int
)

In this example, @Id marks the identifier and @GeneratedValue asks the database to generate it.

Declare a repository as a trait extending CrudRepository. Methods such as findByTitle describe queries through their names:

/** Books, stored in the default data source. */
@JdbcRepository(dialect = Dialect.H2)
trait BookRepository extends CrudRepository[Book, Long]:

  /** Finds every book with the given title. */
  def findByTitle(title: String): List[Book]

  /** Counts the books longer than the given length. */
  def countByPagesGreaterThan(pages: Int): Long

  /** Finds one book with the given title, if there is one. */
  def findFirstByTitle(title: String): java.util.Optional[Book]

During compilation, Micronaut Data processes the entity and repository and records the SQL and query metadata. Micronaut generates a repository proxy whose interceptors execute those queries at runtime. You inject BookRepository without writing an implementation yourself.

Scala collections can be used for query results, but optional single results currently need java.util.Optional. See Micronaut Data for the processor dependency, supported signatures and a database configuration.

The examples in this chapter are compiled and exercised in test-suite-scala and test-suite-scala-data.

4 Idiomatic Scala

Micronaut works well with Scala constructor parameters, case classes and traits. The examples below show how to use those features for beans and configuration, with a few details to keep in mind when using Java APIs.

Prefer constructor injection

Declare dependencies as constructor parameters so they are available throughout the class body, including when initialising a val:

@Singleton
class ReportService(clock: Clock, config: ServerConfig):
  // A constructor parameter is in scope for the class body, so state derived
  // from a dependency can be a val rather than something set later.
  private val label: String = s"${config.host}@${clock.getZone}"

  def report(): String = label

With field injection, a declaration such as @Inject var clock: Clock = null remains null until injection runs. Constructor injection avoids that intermediate state and lets unit tests construct the class directly with test dependencies.

Case classes for configuration

A case class makes a convenient immutable configuration bean:

@ConfigurationProperties("server")
case class ServerConfig(
    host: String = "localhost",
    port: Int = 8080,
    tags: List[String] = Nil,
    banner: Option[String] = None
)
Default parameter values

The constructor default is used when the property is absent. Here, host defaults to localhost; server.host overrides it.

Option[String]

An optional property binds to None when absent.

List[String]

A list-valued property binds to a Scala list, with element conversion. Scala Seq, Set and Map are also supported.

case

Generated equality and toString methods help when comparing configuration values in tests or inspecting them while debugging.

Use class-level Scaladoc @param tags to document constructor properties in generated configuration metadata. See Documentation in Generated Files.

Binding Option and Scala collections requires micronaut-runtime-scala on the runtime classpath.

Repeated configuration

Use @EachProperty when the same configuration structure appears under several names, such as a set of data sources. @Parameter receives each entry’s name:

@EachProperty("datasources")
case class DataSourceConfig(@Parameter name: String, url: String)

Configuring datasources.one.url and datasources.two.url creates two DataSourceConfig beans. Inject one by name with @Named, or inject a collection to receive them all.

Enums in configuration

For an enum bound from a configuration string, extend java.lang.Enum:

enum Mode extends java.lang.Enum[Mode]:
  case Fast, Slow

@ConfigurationProperties("run")
case class RunConfig(mode: Mode = Mode.Slow)

Configuration binding uses Micronaut’s Java enum converter. A plain Scala enum does not extend java.lang.Enum, so this conversion fails. The example above supports both a configured value and the constructor default when no value is set. JSON serialization has separate support for plain Scala enums; see Serialization.

Use traits for replaceable dependencies

A trait lets a bean depend on an interface while Micronaut supplies an implementation:

trait Notifier:
  def send(message: String): String
@Singleton
class EmailNotifier extends Notifier:
  def send(message: String): String = s"email: $message"

@Singleton
class SmsNotifier extends Notifier:
  def send(message: String): String = s"sms: $message"

When several beans implement the trait, a collection parameter receives all of them:

@Singleton
class Broadcaster(notifiers: List[Notifier]):
  def broadcast(message: String): List[String] =
    notifiers.map(_.send(message)).sorted

If a dependency is optional, declare an Option parameter. It receives None when no matching bean exists:

trait Archive:
  def store(message: String): Unit

@Singleton
class AuditLog(archive: Option[Archive]):
  def describe(): String = archive.fold("not archived")(_ => "archived")

To select one of several implementations, use a qualifier such as @Named at the injection point. This also lets a test supply a different implementation without changing the consuming bean.

Traits can also declare abstract methods implemented by introduction advice, as described in Micronaut for Scala Developers.

Factories for types you do not own

Use @Factory to create beans from library types or to centralise construction logic. Each method annotated with a scope supplies a bean of its return type:

@Factory
class Clocks:
  @Singleton
  def systemClock(): Clock = Clock.systemUTC()

The Clock returned by this factory can be injected into ReportService.

Scala objects as beans

A Scala object can be annotated with @Singleton:

@Singleton
object HouseStyle:
  def prefix: String = "[app]"

@Singleton
class Banner(style: HouseStyle.type):
  def render(text: String): String = s"${style.prefix} $text"

In this example, the injection point uses HouseStyle.type, the singleton type of that specific object. A test double cannot have the same singleton type. For behaviour you may want to replace, prefer a class injected through a trait. Objects remain useful for constants and pure helper functions.

AOP and annotation rules

AOP proxies extend your bean class and override advised methods. Keep advised classes and methods non-final so the compiler can generate those overrides.

Java annotation arguments also follow Scala’s rules: use explicit arrays for array-valued members and name annotation arguments. See Annotations for examples.

These examples are compiled and run by GuideExamplesSpec in test-suite-scala.

5 Build Tools

Register Micronaut Scala as a Scala compiler plugin. The configuration depends on your build tool, but the artifact name must always match the full Scala compiler version. The examples below use Scala 3.10.0 and JDK 25.

Gradle

Use Gradle’s scalaCompilerPlugins configuration for the plugin:

plugins {
    scala
}

repositories {
    mavenCentral()
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(25)
    }
}

dependencies {
    implementation("org.scala-lang:scala3-library_3:3.10.0")
    implementation("io.micronaut:micronaut-context:5.2.2")

    scalaCompilerPlugins("io.micronaut.scala:micronaut-inject-scala_3.10.0:1.0.0-SNAPSHOT")
    runtimeOnly("io.micronaut.scala:micronaut-runtime-scala:1.0.0-SNAPSHOT")
}

tasks.withType<ScalaCompile>().configureEach {
    options.release.set(25)
    scalaCompileOptions.additionalParameters.add("-J--add-modules=java.compiler")
}

The java.compiler module provides the javax.lang.model APIs used by Micronaut processing code. Pass -J—​add-modules=java.compiler to make it available in the compiler process.

The repository’s ScalaGradlePluginFunctionalSpec exercises plugin loading and bean generation through a separate Gradle build, using local jar files as dependencies.

Maven

Register the compiler plugin in scala-maven-plugin’s `compilerPlugins configuration. Add runtime support as an application dependency:

<properties>
  <scala.version>3.10.0</scala.version>
  <micronaut.scala.version>1.0.0-SNAPSHOT</micronaut.scala.version>
</properties>

<dependencies>
  <dependency>
    <groupId>org.scala-lang</groupId>
    <artifactId>scala3-library_3</artifactId>
    <version>${scala.version}</version>
  </dependency>
  <dependency>
    <groupId>io.micronaut.scala</groupId>
    <artifactId>micronaut-runtime-scala</artifactId>
    <version>${micronaut.scala.version}</version>
    <scope>runtime</scope>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <groupId>net.alchim31.maven</groupId>
      <artifactId>scala-maven-plugin</artifactId>
      <configuration>
        <args>
          <arg>-J--add-modules=java.compiler</arg>
        </args>
        <compilerPlugins>
          <compilerPlugin>
            <groupId>io.micronaut.scala</groupId>
            <artifactId>micronaut-inject-scala_3.10.0</artifactId>
            <version>${micronaut.scala.version}</version>
          </compilerPlugin>
        </compilerPlugins>
      </configuration>
    </plugin>
  </plugins>
</build>

This fragment assumes the rest of the application’s Micronaut dependencies and the Scala Maven plugin version and compile executions are configured.

sbt

The example names the complete artifact ID explicitly:

scalaVersion := "3.10.0"

libraryDependencies ++= Seq(
  "io.micronaut" % "micronaut-context" % "5.2.2",
  "io.micronaut.scala" % "micronaut-runtime-scala" % "1.0.0-SNAPSHOT" % Runtime
)

addCompilerPlugin(
  "io.micronaut.scala" % "micronaut-inject-scala_3.10.0" % "1.0.0-SNAPSHOT"
)

javacOptions ++= Seq("--add-modules", "java.compiler")

If you use sbt’s cross dependency notation instead, select CrossVersion.full. The default binary-version suffix _3 does not identify a published plugin.

Mill

Add the plugin to scalacPluginIvyDeps, using its full artifact ID:

object app extends ScalaModule {
  def scalaVersion = "3.10.0"

  def ivyDeps = Agg(
    ivy"io.micronaut:micronaut-context:5.2.2",
    ivy"io.micronaut.scala:micronaut-runtime-scala:1.0.0-SNAPSHOT"
  )

  def scalacPluginIvyDeps = Agg(
    ivy"io.micronaut.scala:micronaut-inject-scala_3.10.0:1.0.0-SNAPSHOT"
  )

  def scalacOptions = Seq("-J--add-modules=java.compiler")
}

When using Mill’s cross-version notation instead of an explicit suffix, use the full-cross ::: form.

The repository tests the Gradle integration. The Maven, sbt and Mill fragments are not exercised here. If compilation produces no bean definitions, see Troubleshooting.

6 Configuration Options

Options are passed to the plugin with the standard Scala compiler-plugin syntax:

-P:micronaut-scala:<key>=<value>

An option without = has the value "true".

Available options

The plugin passes options to VisitorContext.getOptions(). Micronaut processing code and any TypeElementVisitor on the compilation classpath can read them, so visitors may accept additional keys beyond those listed here.

The table lists the well-known keys in the plugin’s help. Their effect depends on the processing code that reads them. Use -P:micronaut-scala:help to print the help.

Key Meaning

micronaut.processing.incremental

Incremental processing hint (true or false). This does not make build tools track generated bean definitions; see Limitations.

micronaut.processing.group

The Maven group of the module being compiled.

micronaut.processing.module

The name of the module being compiled.

micronaut.processing.project.dir

The project directory passed to processing code.

micronaut.processing.annotations

Comma-separated package prefixes for processors that support annotation filtering.

micronaut.processing.use.context.classloader

Micronaut’s context-classloader switch. The Scala integration enables context classloader lookup internally while processing.

Setting options

tasks.withType<ScalaCompile>().configureEach {
    scalaCompileOptions.additionalParameters.addAll(
        listOf(
            "-J--add-modules=java.compiler",
            "-P:micronaut-scala:micronaut.processing.group=com.example",
            "-P:micronaut-scala:micronaut.processing.module=app"
        )
    )
}
The plugin accepts unknown keys. Check the spelling if an option has no effect; a typo does not cause a compilation error.

7 Annotations

Micronaut uses Java annotations. When applying them in Scala, use explicit arrays, name the arguments and write repeatable-annotation containers yourself. These differences matter when adapting examples from Java.

Array-valued members

Java allows a single value for an array-valued annotation member. Scala requires an array, even for one element. This does not compile:

@Introspected(accessKind = Introspected.AccessKind.METHOD)   // does not compile
Found:    (io.micronaut.core.annotation.Introspected.AccessKind.METHOD :
  io.micronaut.core.annotation.Introspected.AccessKind)
Required: Array[io.micronaut.core.annotation.Introspected.AccessKind]

Wrap the value in Array(…​):

@Introspected(accessKind = Array(Introspected.AccessKind.METHOD))
class Vehicle(val make: String)

Named arguments

Use named arguments for Java annotation members. A positional argument can bind to the first declared member rather than value. For example, @Min(10) binds to the message member of jakarta.validation.constraints.Min and fails:

def check(@Min(10) size: Int): Int = size   // does not compile
Found:    (10 : Int)
Required: String

Name the member explicitly:

@Introspected
class Part:
  @Introspected.Property(value = "part_number")
  def partNumber: String = "none"
  def partNumber_=(value: String): Unit = ()

An annotation whose only member is value also accepts a positional argument. Naming it still makes the intent clear.

Repeatable annotations

Scala does not accept repeated applications of the same annotation. Use the container annotation declared by Java’s @Repeatable, with new for each entry:

@Retention(RetentionPolicy.RUNTIME)
@Target(Array(ElementType.TYPE, ElementType.METHOD))
@InterceptorBindingDefinitions(Array(
  new InterceptorBinding(kind = InterceptorKind.POST_CONSTRUCT),
  new InterceptorBinding(kind = InterceptorKind.PRE_DESTROY)
))
class Managed extends StaticAnnotation, java.lang.annotation.Annotation:
  override def annotationType(): Class[? <: java.lang.annotation.Annotation] =
    classOf[Managed]

For Micronaut annotations, common pairs are @Requires and @Requirements, @InterceptorBinding and @InterceptorBindingDefinitions, and @Property and @PropertySource.

Declaring an annotation

A Scala annotation extends scala.annotation.StaticAnnotation and declares its members as constructor parameters. Use @Retention(RetentionPolicy.RUNTIME) for Micronaut annotation processing and @Target to specify where it applies:

@Retention(RetentionPolicy.RUNTIME)
@Target(Array(ElementType.TYPE))
class Audited(val category: String = "general") extends StaticAnnotation

@Audited(category = "billing")
class Invoice(val total: Long)

If another annotation accepts your annotation type as a classOf[…​] argument bounded by Annotation, also extend java.lang.annotation.Annotation and implement annotationType(), as Managed does above. Examples of such arguments include those of @InterceptorBean, @Type and @Introduction(interfaces = …​).

Scala and Java type names

Check which type a short name refers to. Scala’s StringBuilder is scala.collection.mutable.StringBuilder; use java.lang.StringBuilder when a Java API or injection point needs that type.

Similarly, Scala Seq, List and Map differ from Java collections. The runtime support converts between supported collection types, but the types are not interchangeable in method signatures.

8 Documentation in Generated Files

The compiler plugin makes Scaladoc comments available to Micronaut’s compile-time visitors. Those visitors can use the comments for descriptions in configuration metadata, OpenAPI definitions and JSON schemas.

Write Scaladoc comments

No compiler flag or plugin option is needed. Use /** …​ */ comments above the declarations you want to document; ordinary // comments are not included.

For a constructor property, write a class-level @param tag:

/** Configures the outbound mailer.
  *
  * @param host the SMTP host to connect to
  * @param port the port the SMTP host listens on
  */
@ConfigurationProperties("mailer")
case class MailerConfig(host: String = "localhost", port: Int = 25)

The generated configuration metadata includes the class description and each parameter’s description:

{
  "groups": [
    { "name": "mailer",
      "type": "io.micronaut.docs.documentation.MailerConfig",
      "description": "Configures the outbound mailer." }
  ],
  "properties": [
    { "name": "mailer.host", "type": "java.lang.String",
      "description": "the SMTP host to connect to" },
    { "name": "mailer.port", "type": "int",
      "description": "the port the SMTP host listens on" }
  ]
}

For a property declared in the class body, put the comment directly above it:

@ConfigurationProperties("mailer")
class MailerConfig:
  /** How many messages to send at once. */
  var batchSize: Int = 10

Place the main description before any block tags such as @param, @return or @throws. The description ends at the first block tag.

Where descriptions appear

Configuration metadata

Compiling @ConfigurationProperties classes generates META-INF/spring-configuration-metadata.json. The class comment describes the configuration group, and property comments or @param tags describe its keys. IDEs can display these descriptions during configuration completion.

OpenAPI

Add micronaut-openapi to the compilation classpath to generate an OpenAPI definition. Its visitor can use comments on controller methods and exposed types for operation and schema descriptions. Explicit descriptions in annotations such as @Schema take precedence.

JSON schema

A JSON schema generator can read the same documentation through Micronaut’s element API. Add the generator required by your application to the compilation classpath.

Comments from dependencies

The plugin reads comments from the sources being compiled. Class files from another module or library do not retain Scaladoc, so those types do not provide comments through this mechanism. If needed, document the member that exposes the dependency type in your own sources.

GuideExamplesSpec checks the generated metadata for the MailerConfig example. OpenAPI examples and generation tests are in test-suite-scala-openapi.

9 Serialization

Micronaut Serialization uses the introspections generated by the compiler plugin to read and write Scala objects. Annotate a case class with @Serdeable to enable serialization and deserialization:

/** One line of an order. */
@Serdeable
case class Line(sku: String, quantity: Int)

This example writes as {"sku":"sku-1","quantity":2}. Deserialization calls the case class constructor with the property values.

Add the serialization implementation and Scala runtime support:

implementation("io.micronaut.serde:micronaut-serde-jackson")
<dependency>
    <groupId>io.micronaut.serde</groupId>
    <artifactId>micronaut-serde-jackson</artifactId>
</dependency>

runtimeOnly("io.micronaut.scala:micronaut-runtime-scala")
<dependency>
    <groupId>io.micronaut.scala</groupId>
    <artifactId>micronaut-runtime-scala</artifactId>
    <scope>runtime</scope>
</dependency>

The runtime module supplies serializers and deserializers for Scala Option, collections and enums.

A worked example

The following order combines these types:

/** A customer order.
  *
  * @param reference the order reference
  * @param status how far along it is
  * @param lines what was ordered
  * @param notes free text the customer may not have supplied
  * @param labels arbitrary tags, by name
  */
@Serdeable
case class Order(
    reference: String,
    status: Status,
    lines: List[Line],
    notes: Option[String] = None,
    labels: Map[String, String] = Map.empty
)

An order with one line and all optional values supplied writes as:

{
  "reference": "A-1",
  "status": "Placed",
  "lines": [{"sku": "sku-1", "quantity": 2}],
  "notes": "leave at the door",
  "labels": {"priority": "high"}
}

Option

Some(value) writes the contained value without a wrapper. With the default inclusion settings, a property containing None is omitted. The serializer reports an empty option as absent; if it is written explicitly, it writes as JSON null.

Give optional constructor parameters a default of None:

notes: Option[String] = None

When the JSON omits the property, Micronaut Serialization uses the constructor default. Without that default, an omitted Option property currently receives null. An explicit JSON null, however, deserializes to None even without a constructor default.

This missing-property behaviour is covered by the serialization tests and is tracked in micronaut-serialization#1416.

Defaults also work for collections. For example, labels: Map[String, String] = Map.empty gives an omitted labels property an empty map.

Collections

Scala collections such as List, Seq, Set, Vector and IndexedSeq write as JSON arrays. Maps write as JSON objects, with their keys represented as strings. During deserialization, elements, keys and values are read using the declared type arguments. For example, List[Line] uses the Line deserializer for each element, and Map[Int, String] converts JSON property names to integers.

The result matches the declared collection type: Vector[Int] produces a Vector, while Seq[String] produces a compatible sequence. Supported mutable collection interfaces include mutable.Seq, mutable.Set, mutable.Buffer, mutable.IndexedSeq and mutable.Map.

Deserialization uses the collection converters registered by micronaut-runtime-scala. A custom collection type needs a converter that can produce that type.

Scala 3 enums

An enum with parameterless cases writes as its case name:

/** How far along an order is. */
enum Status:
  case Placed, Shipped, Delivered

Deserialization looks up the name using the compiler-generated valueOf method. Unknown names cause a deserialization error. Serialization uses the case name even if the enum overrides toString.

The enum does not need its own @Serdeable annotation. Enums with parameterised cases do not have the required valueOf method and are not supported by this serializer. Model those values with a suitably configured serializable hierarchy or provide a custom serializer.

Other serialization features

Micronaut Serialization’s documentation covers supported Jackson annotations, naming strategies, views and custom serializers. Use @Serdeable.Serializable for serialization only and @Serdeable.Deserializable for deserialization only. See Annotations for Scala’s rules when supplying Java annotation arguments.

The examples in this chapter are compiled and tested with an ObjectMapper in test-suite-scala-serde.

10 Micronaut Data

Micronaut Data generates query metadata at compile time and implements repository methods through introduction advice. Scala entities can be case classes, and repositories can be traits or abstract classes.

Dependencies

Add the Data processor to the compilation classpath of the module containing your Scala entities and repositories. The Scala plugin discovers its TypeElementVisitor through that classpath:

compileOnly("io.micronaut.data:micronaut-data-processor")
<dependency>
    <groupId>io.micronaut.data</groupId>
    <artifactId>micronaut-data-processor</artifactId>
    <scope>provided</scope>
</dependency>

An annotationProcessor dependency alone is insufficient for Scala. That configuration is used by javac. A module with both Java and Scala entities needs the processor in both configurations.

Without the processor on the Scala compilation classpath, a repository proxy may still be generated, but calling it can fail with Micronaut Data method is missing compilation time query information.

For JDBC access to the in-memory H2 database used here, add:

implementation("io.micronaut.data:micronaut-data-jdbc")
<dependency>
    <groupId>io.micronaut.data</groupId>
    <artifactId>micronaut-data-jdbc</artifactId>
</dependency>

runtimeOnly("io.micronaut.sql:micronaut-jdbc-hikari")
<dependency>
    <groupId>io.micronaut.sql</groupId>
    <artifactId>micronaut-jdbc-hikari</artifactId>
    <scope>runtime</scope>
</dependency>

runtimeOnly("com.h2database:h2")
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>runtime</scope>
</dependency>

Also add the runtime converters for Scala collection results:

runtimeOnly("io.micronaut.scala:micronaut-runtime-scala")
<dependency>
    <groupId>io.micronaut.scala</groupId>
    <artifactId>micronaut-runtime-scala</artifactId>
    <scope>runtime</scope>
</dependency>

See Artifacts and Dependencies for more about visitor loading.

Define an entity

Annotate a case class with @MappedEntity. Put the property annotations on its constructor parameters:

/** A book on the shelf.
  *
  * @param id the generated primary key, zero until the database assigns one
  * @param title the book's title
  * @param pages how many pages it has
  */
@MappedEntity
case class Book(
    @Id @GeneratedValue id: Long,
    title: String,
    pages: Int
)

The plugin makes those annotations available on the properties Micronaut Data processes. @Id marks the identifier, and @GeneratedValue requests a database-generated value.

The identifier uses Scala Long, which maps to Java’s primitive long. A new entity starts with id set to 0; the entity returned by save contains the generated identifier.

Define a repository

Extend CrudRepository to inherit the standard persistence operations. Add methods whose names describe queries:

/** Books, stored in the default data source. */
@JdbcRepository(dialect = Dialect.H2)
trait BookRepository extends CrudRepository[Book, Long]:

  /** Finds every book with the given title. */
  def findByTitle(title: String): List[Book]

  /** Counts the books longer than the given length. */
  def countByPagesGreaterThan(pages: Int): Long

  /** Finds one book with the given title, if there is one. */
  def findFirstByTitle(title: String): java.util.Optional[Book]

findByTitle finds matching rows, and countByPagesGreaterThan counts rows with a larger page count. The type arguments in CrudRepository[Book, Long] tell Micronaut Data which entity and identifier types the inherited operations use.

The compiler plugin and Data processor generate the proxy and query metadata. Inject BookRepository to use it; you do not need to implement the abstract methods. Concrete methods on the trait or abstract class retain their own implementation.

Scala types in method signatures

findByTitle returns a Scala List[Book]. At compile time, the plugin identifies Scala collections as iterable results so Data can process a multi-row query. At runtime, the Scala converters turn the result collection into the declared type.

countByPagesGreaterThan returns Scala Long, represented as a primitive.

For an optional single result, use java.util.Optional, as findFirstByTitle does. Micronaut Data currently rejects scala.Option for this signature:

Unable to implement Repository method: BookRepository.findFirstByTitle(String title).
Query results in a type [Book] whilst method returns an incompatible type: scala.Option

To convert the result to Scala Option, import scala.jdk.OptionConverters.* and call .toScala.

Configuration and testing

The example repository uses the default data source. Configure an in-memory H2 database with schema creation enabled:

datasources:
  default:
    url: jdbc:h2:mem:books;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE
    driver-class-name: org.h2.Driver
    username: sa
    password: ""
    schema-generate: CREATE_DROP
    dialect: H2

In a test, start an ApplicationContext with these properties, retrieve the repository and call its methods.

The examples are compiled and run against H2 in test-suite-scala-data. That module also compares generated query metadata with an equivalent Java repository.

Compiler plugin

micronaut-inject-scala_3.10.0 runs inside the Scala compiler. It bundles the Micronaut and ASM classes it needs because the compiler loads plugins in an isolated classloader.

Most bundled dependencies are omitted from the published POM to avoid resolving them again as separate plugin jars. Keep the compiler plugin on the compiler plugin configuration: putting it on an application’s runtime classpath can introduce conflicting copies of Micronaut and ASM.

Runtime support

micronaut-runtime-scala supplies converters for Scala collections and Option. It also provides serializers and deserializers when Micronaut Serialization is present. Include it at runtime when your application uses these features.

This artifact has no compiler-version suffix because it does not run inside the compiler.

Compile-time visitors

The Scala plugin discovers TypeElementVisitor implementations through ServiceLoader on the compilation classpath. Processors from other Micronaut modules, such as validation or Data, must therefore be compile-time dependencies of the module containing your Scala sources.

Adding a processor only to Gradle’s annotationProcessor configuration makes it available to javac, not to the Scala plugin. Use compileOnly for a processor needed by Scala sources.

Visitors load their dependencies from the compilation classpath in preference to the compiler process’s own libraries. They share the JDK, Scala compiler classes and classes bundled with the plugin. This keeps libraries used by a visitor, such as Jackson or SnakeYAML, separate from versions used by the build tool’s compiler infrastructure.

Versions

The suffix identifies the full Scala compiler version. For example, micronaut-inject-scala_3.10.0 is published; micronaut-inject-scala_3 is not. See Supported versions for the available compiler variants.

The Micronaut Scala release version is independent of the Micronaut Core version.

12 Testing

micronaut-inject-scala-test_<scala version> provides a harness for compiling Scala sources in-process and inspecting the resulting elements, bean definitions and introspections. It can also start an ApplicationContext from the compiled classes.

Use this harness when developing the Scala integration or a compile-time visitor. Application tests can use the normal Micronaut testing APIs without it.

Add the harness

testImplementation("io.micronaut.scala:micronaut-inject-scala-test_3.10.0")
<dependency>
    <groupId>io.micronaut.scala</groupId>
    <artifactId>micronaut-inject-scala-test_3.10.0</artifactId>
    <scope>test</scope>
</dependency>

The artifact suffix must match the full Scala compiler version. See Artifacts and Dependencies.

Set the system properties

The harness invokes the Scala compiler directly. Supply both of these properties so it can locate the plugin and resolve the compiled source’s dependencies:

Property Value

micronaut.scala.plugin.jar

Absolute path to the compiler plugin jar.

micronaut.scala.test.classpath

Classpath for the compiled sources, usually the test runtime classpath.

For a Gradle test task, with pluginJar referring to the built plugin jar:

tasks.withType<Test>().configureEach {
    doFirst {
        systemProperty("micronaut.scala.plugin.jar", pluginJar.absolutePath)
        systemProperty(
            "micronaut.scala.test.classpath",
            sourceSets.test.get().runtimeClasspath.asPath
        )
    }
}

Using doFirst defers classpath resolution until the test task runs. The harness reports an error if either required property is missing.

Compile and inspect sources

AbstractScalaTypeElementSpec provides these helpers:

  • buildClassElement(name, source) compiles source and returns its ClassElement.

  • buildBeanDefinition(name, source) compiles and loads a bean definition.

  • buildBeanIntrospection(name, source) compiles and loads an introspection.

  • buildContext(source, properties, includeAllBeans) compiles source and starts an ApplicationContext.

  • buildClassLoader(name, source) compiles source and returns a classloader for the output.

A test can install a visitor for a compilation to capture the VisitorContext and inspect the elements produced by the compiler.

13 Limitations

This chapter describes known limitations and Scala bytecode details that can affect compile-time visitors.

Incremental compilation

Generated bean definitions are written directly into the class output directory. Build tools do not track them as outputs belonging to a particular source file. Deleting or renaming a bean’s source can therefore leave its generated definition and registration marker behind.

For example, $Foo$Definition.class and its marker under META-INF/micronaut/io.micronaut.inject.BeanDefinitionReference/ may survive an incremental rebuild. The application can then still discover the old bean. A compilation that fails after generating files can also leave stale output.

Run a clean build after deleting or renaming a bean, or when stale generated classes remain after a failed compilation.

Recompiling only some sources does retain the definitions for unchanged sources. Each bean has its own registration marker, so a partial compilation does not replace a shared list of all beans.

Scala bytecode and the element model

When writing a visitor, keep these differences from Java source in mind:

  • A repeated parameter such as def f(xs: String*) is represented as a single scala.collection.immutable.Seq parameter. The method has no JVM varargs flag, so isVarArgs() returns false.

  • Scala protected and protected[pkg] members can be public in the bytecode. The element model reports that JVM visibility.

  • Scala val and var properties have private backing fields and accessor methods. A query for public fields will not find those backing fields.

The model also includes trait parameters, inline methods and extension methods declared in a class body.

14 Troubleshooting

No bean definitions are generated

If compilation succeeds but produces no $*$Definition classes, check that the plugin is registered with the Scala compiler. Use scalaCompilerPlugins, addCompilerPlugin, scalacPluginIvyDeps or Maven’s compilerPlugins, as shown in Build Tools. An ordinary application dependency does not load the plugin.

Run the compiler with -Xplugin-list to check which plugins loaded. Also check that the source declares a bean, for example with @Singleton.

NoClassDefFoundError inside the compiler

java.lang.NoClassDefFoundError: io/micronaut/inject/processing/ProcessingException

Check that you are using the published compiler plugin jar with its bundled dependencies. A jar containing only this project’s classes lacks the Micronaut and ASM classes needed during processing.

The Scala compiler loads a plugin from its -Xplugin path in a separate classloader. In Gradle, each resolved plugin jar gets its own -Xplugin argument, so adding the missing dependencies as separate plugin entries does not make them visible to the plugin. Use the complete bundled jar.

Missing plugin.properties warnings

warning: Missing plugin.properties in <some-jar>

A jar passed to -Xplugin has no plugin descriptor. This can happen when the build tool resolves transitive dependencies into the compiler plugin configuration. The compiler skips those jars.

Check the resolved plugin configuration. The Micronaut Scala plugin jar itself must contain plugin.properties at its root.

Errors mentioning javax.lang.model

Make the java.compiler module available in the compiler process:

-J--add-modules=java.compiler

See Build Tools for the compiler configuration examples.

Could not find …​_3:<version>

Use the full Scala compiler version in the plugin artifact name. For example, this project publishes micronaut-inject-scala_3.10.0, not micronaut-inject-scala_3.

With cross-version notation, use CrossVersion.full in sbt or ::: in Mill. With explicit coordinates, write the full suffix in the artifact ID.

Scala collections or Option fail to bind

If configuration binding or injection involving a Scala collection or Option fails at runtime, check that micronaut-runtime-scala is on the runtime classpath. Its converters are separate from the compiler plugin. Also check that the configured values can be converted to the declared element type.

See Artifacts and Dependencies.

The version of 'scala-library' was changed while using the default Zinc version

Version 3.9.0 is not compatible with org.scala-sbt:zinc_2.13:1.12.0

Check whether a dependency-resolution rule is applying your Scala 3 version to Gradle’s zinc configuration. Zinc needs its own Scala 2.13 scala-library and scala-reflect dependencies. Exempt that configuration from application Scala version pinning.

A deleted bean is still available

Run a clean build after deleting or renaming a bean. Build tools do not track the generated bean definition as an output of its source, so an incremental build can leave the definition behind. See Limitations.

A plugin option has no effect

The plugin passes -P:micronaut-scala: options to VisitorContext.getOptions() and accepts unknown keys. Check the spelling and confirm that the visitor using the option is on the compilation classpath. See Configuration Options.

The repository separates shared sources from compiler-specific builds:

  • inject-scala contains the compiler plugin implementation.

  • inject-scala-test contains the compiler test harness and parity tests.
