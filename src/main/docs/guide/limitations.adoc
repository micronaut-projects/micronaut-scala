This chapter describes known limitations and Scala bytecode details that can
affect compile-time visitors.

== Incremental compilation

Generated bean definitions are written directly into the class output directory.
Build tools do not track them as outputs belonging to a particular source file.
Deleting or renaming a bean's source can therefore leave its generated definition
and registration marker behind.

For example, `$Foo$Definition.class` and its marker under
`META-INF/micronaut/io.micronaut.inject.BeanDefinitionReference/` may survive an
incremental rebuild. The application can then still discover the old bean.
A compilation that fails after generating files can also leave stale output.

Run a clean build after deleting or renaming a bean, or when stale generated
classes remain after a failed compilation.

Recompiling only some sources does retain the definitions for unchanged sources.
Each bean has its own registration marker, so a partial compilation does not
replace a shared list of all beans.

== Scala bytecode and the element model

When writing a visitor, keep these differences from Java source in mind:

* A repeated parameter such as `def f(xs: String*)` is represented as a single
  `scala.collection.immutable.Seq` parameter. The method has no JVM varargs flag,
  so `isVarArgs()` returns `false`.
* Scala `protected` and `protected[pkg]` members can be public in the bytecode.
  The element model reports that JVM visibility.
* Scala `val` and `var` properties have private backing fields and accessor
  methods. A query for public fields will not find those backing fields.

The model also includes trait parameters, `inline` methods and extension
methods declared in a class body.
